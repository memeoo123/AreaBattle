# 游戏美术风格替换

把现有游戏的视觉语言换成一致、可读、可运行的新风格。以项目的真实渲染方式为依据，分别处理概念图、生产资源和运行时表现。当前包含 Unity 接入指引；其他引擎先检查项目的资源与运行接口，再适配，不能声称已验证。

## 确定本轮终点

从当前请求与已有决定确定模式，不重复询问已确认的偏好：

- **盘点/规划**：读取代码、资源和截图，输出范围与方案，不生成整批图片或修改游戏。
- **风格探索/样板设计**：制作用户要求的概念图或少量核心素材，明确哪些只是效果预览。
- **可玩样板**：接入一组代表性资源，在真实引擎中验证动态状态。
- **批量替换**：沿已确定风格补齐资产及状态；不重新发散方向。
- **验收/继续**：读取上次状态和当前差异，仅补做被改动影响的检查。

“创建这个 skill”不等于授权开始实际美术替换。保留玩法、关卡布局、碰撞、射程、输入和存档语义，除非用户另外要求改变。把运行时多风格切换视为独立功能，仅在用户要求时实现配置、缓存刷新和状态保留。

## 阶段关卡（必须遵守）

按 inventory → style-selection → sample → rollout → acceptance 推进，在项目记录中保存当前阶段与通过依据。不得用生成成功、编译通过或对局部造型的反馈替代用户的整体风格选择。

- **风格选择关卡**：方向未定时，必须先交付可比较的风格方案，再请用户选择。选择前仅可盘点、生成比较概念图和验证技术可行性，不得批量生产或替换正式运行资源。用户已明确指定风格、参考或授权自行定风格时，记录依据后直接进入样板，不重复索取确认。
- **样板关卡**：沿选定风格制作最小代表组并接入可玩样板，检查真实占屏尺寸、状态和交互。批量扩展前必须具有样板验证证据；用户要求先试或先看时，须获得对该样板的反馈再扩展。完整落地已获授权时，检查通过即可继续。
- **验收关卡**：只有与本次版本匹配的检查才能作为通过证据；视觉认可与技术通过分别记录。
- “继续”“试一版”仅延续当前明确阶段；不得把试验许可自动记成最终风格确认。用户要求重启时，保留既有资产为历史试验，清空当前风格选择状态，不删除已完成工作。
- 用户明确调整流程或授权跳过某阶段时遵从用户，记录覆盖范围；不得自行以节省时间为由跳过。

## 1. 盘点真实资源链

读取项目约束、交接、版本控制状态及已有美术方案。检查少量代表资源，记录：加载入口 → Prefab/图片/模型 → Renderer/材质 → 动画驱动 → 游戏状态映射。实际查看现有画面；历史截图只能作为历史基线。

对背景、塔/建筑、士兵、Boss、障碍、连线、特效和界面分别判断：Sprite、平面网格、序列帧、实时骨骼、烘焙顶点动画或立体模型。**MeshRenderer 不等于立体模型，项目包含 Spine 库不等于所有单位都实时使用 Spine。** 引用支持结论的文件，未知项注明未验证。

识别共享资源是否也被关外界面或旧入口引用。按用户范围复制或配置覆盖，避免修改共享文件意外影响其他模式。

执行工具路由时读取 [tools-and-production.md](references/tools-and-production.md)。AreaBattle 实例读取 [area-battle-example.md](references/area-battle-example.md)，其规则不得套用到其他游戏。

## 2. 建立风格与资源约定

沿用户参考和已有选择推进。方向未定时，通常制作2～3个视觉语言明显不同的候选，而非只换配色。每个方案使用同一布局、镜头、对象类型与相近占屏尺寸，覆盖背景、核心建筑、运动单位和代表障碍；标明是概念图。可以附局部放大，但不得只用大幅单体精绘让用户判断游戏内表现。生成造成布局漂移时，注明偏差或修正，不宣称精确同场景对照。

先交付具体可评审的方案，再请求选择或混合方向；整体风格和单个对象造型分开确认。对某个塔宽度、材质或士兵外形的认可，不等于整体风格已确认。记录选择证据后再制作生产资源；需要确认时继续独立盘点，但不得越过关卡执行依赖该选择的工作。

风格约定至少覆盖：镜头/透视、形状语言、色板、光照方向、描边、材质感、界面字体层级，以及阵营/种类/等级的辨识方式。用相同布局比较风格，别把构图变化误当美术优劣。

为样板资源指定逻辑 ID、用途、画布与占屏尺寸、锚点、透明度、层级、状态/阵营变体和动画需求。数字、动态文字、交互线条与射程边界交给引擎绘制。阴影是否单独制作取决于运行时需要；不要把固定地面烘进可移动对象。

## 3. 制作与验证代表样板

先做足以验证风格的一组：环境局部、核心对象及变体、一个运动单位、主要交互、核心 HUD。样板范围由游戏决定，不强制固定数量。

概念图标记为概念图。生产素材分别输出，保持统一参照；不要把整张效果图当成可运行场景，也不要把单张角色图当成可播放动画。读工具路由选择合适动画路径。

每次生成记录输入参考、提示词、输出文件与用途。检查实际尺寸、透明通道、裁边、轮廓、透视和小尺寸可读性。遇到偏差用明确的单项修正；同一问题连续两次针对性修正仍失败，改变制作方法或报告具体缺口，不无限生成。

用户要求完整落地且已给定风格时，继续实施，不额外插入强制审批。用户要求先看方案/先讨论时，在约定终点展示结果，等待选择。

## 4. 引擎接入

保留可追溯的原资源与映射；优先新增风格资源目录和轻量配置入口，遵守项目已有架构，不为一次换图构建庞大换肤框架。Unity 中保留现有 .meta/GUID 关系，不删除再重建已引用资源。

将逻辑类型、阵营、等级映射到视觉资源；美术映射不可反向改变模拟数值。处理锚点、缩放、绘制顺序、材质、透明边缘、镜像与动画时钟。更换渲染方式时保留暂停、死亡完成、对象回收及命中时机等契约。

先在样板中检查，再扩展到其余资产。保留用户本地修改与真实存档。运行引擎前确认实例和可用工具，不重复打开同一工程。

## 5. 验收与交接

同一关卡、镜头、分辨率和相近战斗状态对照旧/新画面。覆盖静止、运动、选中、升级/降级、占领、暂停和拥挤场景中与改动相关的状态。特别检查视觉射程与判定一致、贴图边缘、数字遮挡和敌我辨识。

代码改动需要相应编译和行为回归；图片修改以导入及运行画面检查为主，不为简单替换新增重复实现的测试。更换动画/渲染路径或增加大量透明对象时，在可比场景记录性能；不能仅凭截图宣称性能通过。

结果分别标明已设计、已生成、已导入、已运行、已验收。没有可用引擎时可交付资源与接入改动，但明确运行验收未完成。

多阶段任务用 [state-and-delivery.md](references/state-and-delivery.md) 保存最小状态，继续时先复用这些记录。结束说明完成范围、可查看的样板/文件、验证证据及剩余缺口。实际试做发现的通用经验更新主流程，项目专属规则只更新实例参考。
